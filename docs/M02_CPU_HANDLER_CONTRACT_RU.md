# M02: контракт следующего CPU-исполнителя

Статус: **предложение, не реализованное подключение M02**. База аудита — `ceae671452365a84dcff2787b4ac66d7372a4f13` (после PR18). Импорт публичных квитанций в Studio не запускает этот исполнитель. Здесь нет нового расписания, автоматического исполнения либо разрешения модели выбирать произвольный код.

## Выбранная реализация

Существующий builtin `coupled_dynamics` в `workbench/plugins.py` считает абстрактную трёхкомпонентную систему:

`dx_i/dt = -r*x_i + c*(mean(x)-x_i) + forcing_i`, шаг явного Эйлера `dt=0.05`.

Реализация вызывается через `Service.run`, который проверяет `data/builtin_pins.json`, валидирует числовые параметры, запускает закреплённый `plugin_worker.py` отдельным Python-процессом с `-I`, ограничивает время и размер принимаемого ответа. Это уже имеющийся CPU-код, без модели, загрузки данных и сетевого доступа со стороны алгоритма. Он выбран потому, что результат можно проверять по известному инварианту, а не по согласию двух агентов.

Модель безразмерная и не калибрована на организме; она не прогнозирует биологические или клинические исходы. Отдельный процесс не является файловой или сетевой песочницей. В Windows `plugin_worker.py` не устанавливает POSIX-лимиты CPU/RAM: там действуют размер входа/ответа и timeout родителя. Новое подключение должно сохранять это различие в квитанции.

## Закрытый вход

Новый идентификатор предлагаемого обработчика — `m02.cpu.coupled.v1`. Он не входит в текущий allowlist `ProjectDispatcher`; его нельзя выбирать до отдельной реализации, ревью и CI.

Внешний контракт содержит ровно `schema_version`, `project_id`, `task_id`, `revision`, `handoff_id`, `parent_handoff`, `base_commit`, `handler`, `parameters`, `input_sha256`. `schema_version=1`, `handler=m02.cpu.coupled.v1`; `parent_handoff=null` для R1 либо принятый предыдущий handoff для R2. Идентичность/ревизии проверяются против control DB, а не принимаются на веру из очереди. `input_sha256` вычисляет контроллер по каноническому контракту без самого поля хеша; воркер пересчитывает его. `base_commit` — принятый полный lowercase Git SHA. Проект и политика берутся из неизменяемого принятого контракта проекта; пользовательский запрос не может заменить их своим объектом.

`parameters` содержит **все восемь** полей, без дополнительных ключей и неявных defaults:

| Поле | Тип | Допуск нового handler |
|---|---|---|
| `steps` | целое, не bool | 60…240 |
| `replicates` | целое, не bool | 3…12 |
| `recovery` | конечное число, не bool | 0.1…2 |
| `coupling` | конечное число, не bool | 0…1 |
| `load` | конечное число, не bool | 0…1 |
| `perturbation` | конечное число, не bool | 0…2 |
| `uncertainty` | конечное число, не bool | 0…0.4 |
| `seed` | целое, не bool | 0…2147483647 |

Канонический UTF-8 JSON всего входа — не больше 16 KiB. URL, имя модуля, Python, shell, файловый путь, собственные pins, модель, credentials, политика бюджета и исполняемый текст отсутствуют в схеме. Поле `plugin_id` не принимается снаружи: адаптер сам задаёт постоянное `coupled_dynamics`.

## Предел работы и результата

Одна попытка считает `2*replicates+4` траекторий по `steps` шагов, по три скалярных обновления на шаг: максимум `(2*12+4)*240*3 = 20160` обновлений Эйлера. Это счётчик обновлений состояния, **не** число машинных инструкций и не измеренная стоимость CPU. Дополнительно выполняются два процентильных расчёта для каждого из максимум 241 временных отсчётов, сортирующие не больше 12 значений, и конечная сводка интегралов.

Ожидаемый результат: не больше шести рядов по 241 точке, три метрики, две строки таблицы и фиксированные описания модели/ограничений. Принимать только конечные числовые значения, допустимые имена рядов, точную сетку времени и закрытую схему envelope. Ответ — максимум существующего предела 1 MiB; timeout родителя — 10 секунд. В POSIX существующий worker дополнительно устанавливает CPU soft/hard 5/6 секунд, AS 512 MiB, file size 1 MiB и 64 дескриптора. Это не утверждение, что такие ограничения установлены в Windows.

Один handoff резервирует максимум две попытки в прежнем общем монотонном бюджете M02 — 8 резервов на два проекта. Максимальный резерв для этого handler при полном общем бюджете — `8*20160=161280` скалярных обновлений; обслуживание, проверка и сериализация считаются отдельно. Не обнулять бюджет при смене worker, review, restarts или R1→R2. `model_calls=0`, `network_calls=0`, `additional_spend_usd=0`; они описывают именно этот адаптер, а не всю систему.

Хеш доказывает целостность относительно принятого реестра. Он не доказывает научную истинность и не заменяет доверенную проверку кода. Результат сохраняет `calibrated:false`; успешное вычисление не повышает автоматически статус исследования до scientific validation.

## Необходимое соединение с M02

Текущий `network.worker._execute` принимает для `kind=simulation` только `{plugin_id,parameters}`; текущий M02 принимает только `m02.fixture.v1` и фиксированные evidence fixtures. Простая отправка нового вложенного M02 payload существующему generic worker будет отвергнута. Это конкретный незакрытый участок следующей реализации, а не готовая интеграция.

Нужен отдельный проверяемый адаптер маршрутизации: он признаёт только этот versioned handler, связывает очередь с принятым контрактом, валидирует все поля, затем сам строит `{plugin_id:'coupled_dynamics',parameters:...}`. Нельзя доверять worker, который умеет только старую схему: capability объявления и claim должны исключать захват нового задания несовместимым исполнителем. Не использовать чтение полей проекта как разрешение на файловый доступ либо запуск произвольной программы.

Результат попадает в control DB через тот же CAS по project revision/task/handoff/revision/input hash/job ID. Старый R1 не может заменить уже принятый R2; поздняя доставка outbox не меняет current pointer. Просмотр и импорт истории Studio не являются командами dispatch/start/review.

## Восстановление и критерии проверки

Фиксированная проекция `B` включает immutable job identity/input/result, текущий versioned pointer, budget/reservations/attempts, сохранённые артефакты, identity публикации и решения review. Технические метки времени, lease maintenance и кэш отображения исключаются заранее. Требуется отдельно первый ожидаемый эффект, затем `B(S2)=B(S1)` при повторе подтверждённого действия; не равенство исходному пустому состоянию.

- Первый конечный вызов создаёт один результат, один резерв handoff и одну текущую публикацию; повтор принятого контракта не создаёт второй job/reserve/publication.
- При `perturbation=0` baseline и perturbed совпадают, интеграл/остаточная разность равны нулю. Это отрицательный контроль, а не только smoke result.
- Смена `coupling` с 0 на 1 при одинаковых остальных параметрах и seed сохраняет среднее с заданной численной погрешностью (`1e-12` для опубликованных траекторий), но меняет локальную компоненту для фиксированного ненулевого воздействия. Причина: сумма `c*(mean-x_i)` равна нулю. Два одинаковых исполняемых вывода сами по себе такой проверки не дают.
- Отвергнуть bool вместо числа, NaN/Infinity, missing/extra fields, выход за границы, изменённые pins, неизвестный handler и hash mismatch до dispatch/reserve. Изменённый вход под тем же handoff — conflict, а не новая попытка.
- Проверить реальные разрывы после enqueue, сохранения результата, Queue.finish и CAS-promotion; восстановление привязывает те же durable identity. После finish с потерянным ACK сначала читать состояние Queue, не создавать новый handoff/job/reserve.
- Если процесс оборвался после CPU-вычисления, но до любого durable результата, по одной записи «started» нельзя утверждать наличие результата. Повтор чистого CPU-расчёта допустим только в оставшейся ранее зарезервированной попытке и учитывается как новая actual attempt. Это не гарантия exactly-once вычисления. Если исход выполнения/claim нельзя разрешить, фиксировать `outcome_unknown` и ждать восстановления lease/состояния, без сброса бюджета и без нового ключа.
- Два процесса не могут потратить один оставшийся резерв дважды. Отмена до/после finish запрещает новую публикацию, сохраняя историю и уже потраченный бюджет. Обработка недоступного канала не задерживает другой проект.

Будущие новые интеграционные тесты и фактический запуск этого handler выполняются в GitHub Actions/Colab. В рамках документа выполнено только чтение кода и хеширование файлов; новый CPU-процесс не запускался.
