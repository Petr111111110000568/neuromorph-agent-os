# Кооперация вычислительных ролей по аналогии с мозговыми системами
 
Версия реализации: Meta-Harness 0.8. Дата: 24 сентября 2026 года.

Модуль `workbench/brain.py` связывает локальные источники, память прошлых запусков, планирование, распределённую очередь, вычислительные модели и проверку результатов. Это работающий программный координатор. Названия мозговых систем обозначают выбранные разработчиками функции; они не доказывают анатомического соответствия, наличие сознания или способность воспроизвести человеческий мозг.

## Что выполняется

| Программная роль | Фактическая операция | Что получает следующая роль |
|---|---|---|
| Таламус | Проверяет вопрос, seed, класс данных и список разрешённых моделей | Типизированный локальный запрос |
| Ассоциативная кора | Ищет совпадения слов в локальном реестре источников; до 12 записей | ID, URL, название, причина выбора и хеш метаданных |
| Гиппокамп | Находит до 6 результатов завершённых сессий с тем же плагином и отдельных локальных запусков | ID эпизода, сводка, источники и происхождение; без заявления независимой репликации |
| Префронтальная кора | Фиксирует выбранные задачи, все параметры по умолчанию, seed, бюджет и текущий manifest хешей кода | Сохраняемый план |
| Базальные ганглии | Допускает только выбранные встроенные задачи, ставит их в очередь, обеспечивает отмену | До 3 реальных задач для доверенных workers |
| Вычислительный эксперт KAN | Выполняет `kan_benchmark` | Результат сравнения KAN, MLP и линейной модели |
| Вычислительный эксперт последовательностей | Выполняет `cortical_sequence` | Результат контекстных клеток и марковских контролей |
| Вычислительный эксперт пластичности | Выполняет `structural_plasticity` | Адаптация, забывание и стоимость перестройки связей |
| Мозжечок | Сверяет все параметры, хеши входа и результата, manifest кода и структуру численных метрик | Принятая или отклонённая вычислительная ветвь |
| Передняя поясная кора | Сохраняет ошибки; сравнивает результаты по seed внутри одной задачи; отмечает разнонаправленные результаты | Список ограничений и описательных сравнений |
| Общее рабочее пространство | Сводит результаты ветвей с их собственными метриками и областью применимости | Сохраняемый эпизод для пользователя и будущих сессий |

Три вычислительных эксперта не соответствуют трём конкретным анатомическим областям. «Общее рабочее пространство» — программный объект хранения результатов. Роли реализованы правилами Python; внешняя LLM этим модулем не подключается. Формулировка вопроса влияет на локальный отбор метаданных; сама вычислительная задача определяется выбранным плагином. Свободный текст не превращается автоматически в новый эксперимент или биологический прогноз.

Модель KAN решает задачу аппроксимации, модель последовательностей — предсказания символов, модель пластичности — адаптации при смене зависимости. Их итоговые значения нельзя усреднить в «интеллект платформы» или «эффективность эволюции».

## Практический путь пользователя

1. Запустить платформу: `python -m workbench local-network` либо `start.cmd` / `sh start.sh`.
2. Открыть `http://127.0.0.1:8765/brain.html`.
3. Ввести вопрос для локальной организации исследования, выбрать от одной до трёх моделей и seed. `internal` оставляет вопрос в локальной административной области, как и обычный режим этой функции.
4. Создать сессию. Координатор ставит выбранные задачи в существующую очередь; два стандартных доверенных worker-процесса могут выполнять разные ветви.
5. Просмотреть события ролей, результаты экспериментов, происхождение, ограничения и замечания критика.
6. Создать новую сессию с тем же плагином: предыдущий завершённый эпизод станет доступен в памяти. Это повторное использование контекста, а не независимое подтверждение результата.

После закрытия браузера сессия продолжает обновляться, пока работает процесс `local-network`. При остановке программы состояние сохраняется в SQLite. После повторного запуска обновление продолжается. Без запущенных workers состояние `awaiting_workers` нормально и не означает завершённое вычисление.

Источники берутся из местного каталога. Модуль не делает интернет-запросов, не привлекает неизвестных агентов и не выдаёт доступ к федерации. Он может использовать workers на других машинах, если оператор заранее включил их в доверенную сеть платформы. В очередь передаются только `plugin_id` и численные/категориальные параметры синтетического плагина; вопрос и каталог источников туда не входят.

## Контракты

Python: `Brain(service)`. Методы: `status()`, `sessions()`, `get(id)`, `start(body)`, `tick({"id": id})`, `tick_all()`, `cancel({"id": id})`, `export()`, `close()`.

Запрос создания:

```json
{
  "question": "Сопоставить аппроксимацию KAN, контекстную память и структурную пластичность",
  "plugins": ["kan_benchmark", "cortical_sequence", "structural_plasticity"],
  "seed": 42,
  "data_class": "public"
}
```

Обязателен только непустой `question`, не длиннее 2000 символов. По умолчанию выбраны все три плагина, seed 42 и `public`. Seed — целое от 0 до 2147483647; `data_class` — `public` или `internal`. Дубликаты плагинов, произвольные ID, дополнительные поля и невалидные типы отклоняются до записи сессии.

| Локальный HTTP | Результат |
|---|---|
| `GET /api/brain` | Роли, связи, краткие сессии, счётчики и ограничения |
| `GET /api/brain/sessions` | `{items: [краткая сессия]}` |
| `GET /api/brain/session?id=...` | Полная сессия и сведения о заданиях |
| `POST /api/brain/start` | Созданная сессия и поставленные задания |
| `POST /api/brain/tick` | Обновление выбранной сессии; тело `{"id":"..."}` |
| `POST /api/brain/cancel` | Отмена сессии; тело `{"id":"..."}` |
| `GET /api/brain/export` | Полный локальный JSON-экспорт |

MCP предоставляет `brain_status`, `start_brain_session`, `get_brain_session`, `advance_brain_session`, `cancel_brain_session`. Эти инструменты обращаются к тому же состоянию и не запускают скрытые агенты.

В полной сессии есть `sources`, `memory`, `plan`, `jobs`, `job_details`, `branches`, `workspace`, `events`, `issues` и `limitations`. После завершения добавляется `critique`. Каждое событие хранит `id`, `sequence`, `at`, `region`, `type`, `input`, `output`, `provenance`. Хеш сообщения относится к его входу и выходу; он не является цифровой подписью или защитой от владельца базы данных.

## Достоверность и критика

Состояние `completed` выдаётся только когда все выбранные задания завершились, а их конверты прошли структурную проверку. Проверяются идентификатор модели, полные запланированные параметры, хеши входа/выхода, сохранённые хеши встроенного кода и конечные численные метрики. Обновление плагина в середине сессии не делает новый код автоматически допустимым: сравнение идёт с manifest на момент планирования.

Метка принятой ветви — `envelope_consistent_trusted_worker_only`. Самоотчёт доверенного worker и публичные хеши не доказывают честность удалённого вычислителя. Для этого понадобятся иные механизмы: повторное исполнение, доверенная аттестация или независимая проверка. `scientific_validation` и `worker_attestation` остаются `false`.

Критик вычисляет описательные парные разности по seed:

- `KAN − MLP` по test MSE: отрицательное значение означает меньшую ошибку KAN в этом сравнении.
- `context_cells − markov_2` по точности в неоднозначном контексте: положительное значение означает преимущество контекстных клеток в этом сравнении.
- `guided − fixed` по ошибке после смены зависимости: отрицательное значение означает меньшую ошибку направленной перестройки в этом сравнении.

Число побед, проигрышей и совпадений сохраняется вместе со всеми результатами. Смена знака между seed отмечается явно. Это не статистический тест значимости. Ошибки, неудачные seed и противоречия не удаляются; базовые вычислительные таблицы доступны целиком. Между тремя разными задачами общей численной оценки нет.

Если принят лишь часть ветвей, состояние `partial`; если ни одна — `failed`. Некорректный результат не включается в сводку как успешный. Исходный ответ остаётся в записи задания для локальной диагностики. В итоговом workspace `scientific_conclusion` всегда `not_established`.

## Сохранность и пределы

`brain.sqlite3` использует WAL, `synchronous=FULL`, `BEGIN IMMEDIATE` и локальную блокировку. База координатора и база очереди имеют отдельные транзакции. Операция не объявляется общей распределённой атомарной транзакцией: ключ `brain:<session_id>:<plugin_id>` позволяет восстановить уже поставленную задачу после сбоя между двумя коммитами. Повторный tick не создаёт вторую задачу и не повторяет финальные события.

При отмене координатор сначала сохраняет намерение отменить сессию со статусом `cancelling`, затем дополнительно ищет задачи по ключу, даже если их ID не успел записаться в сессию. Если процесс остановится между отменами отдельных заданий, следующий tick продолжит отмену и не возобновит вычисления. После обработки всех заданий статус становится `cancelled`. Аренда отменённой задачи отзывается. Уже начавший вычислять worker может закончить свой локальный процесс, но очередь отвергнет его результат с устаревшей арендой. Эта версия не отправляет принудительный сигнал завершения процесса удалённому worker.

Пределы: 200 сохранённых сессий, 20 активных, 1–3 задания на сессию, до двух попыток получения каждого задания, до 12 источников и 6 эпизодов памяти. Параметры и время каждой модели дополнительно ограничивает существующий plugin runtime. Автоматического расширения вычислительного бюджета и самостоятельного переписывания плана нет.

Публичная сессия не извлекает внутренние эпизоды из памяти. Административный экспорт намеренно содержит все локальные вопросы, в том числе `internal`; интерфейс ограничен loopback, а экспорт следует проверять перед передачей. Токены аренды workers в экспорт не включаются. Класс данных задаёт оператор; он не заменяет проверку прав и содержания.

## Проверки

`python -m unittest tests.test_brain -v` проверяет 15 сценариев: настоящее выполнение трёх плагинов через trusted-worker handler; ввод; численную устойчивость к чрезмерному целому; хеши и параметры; отдельную сохранность неуспешных результатов; повторные ticks; перезапуск; память прошлых сессий; разделение public/internal; восстановление постановки после сбоя; отмену после частичного коммита; восстановление сохранённого намерения отмены; отзыв аренды; чтение двумя координаторами; отсутствие токенов в экспорте.

HTTP-сценарий с отдельными worker-процессами выполняет `scripts/verify_brain.py`; протокол поставки хранится в `examples/brain_workflow_run.json`. Не следует считать один локальный запуск проверкой развёртывания на нескольких физических машинах.
