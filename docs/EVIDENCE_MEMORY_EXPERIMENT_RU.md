# M03: синтетический эксперимент evidence memory

Это один конечный эксперимент стандартной библиотеки Python, без LLM, HTTP,
платных API или исполнения сгенерированного кода. Он сравнивает три способа выбора
источника и использует существующий `workbench/provenance_verifier.py`.
Код и тесты предназначены для запуска в GitHub Actions/Colab. Локально при
подготовке выполнены только запись файлов, статическая рецензия и хеширование
данных; результаты облачного запуска следует проверять по receipt workflow.

## Запуск и артефакты

Из корня принятого checkout в разрешённом облачном runner:

```text
python -m workbench.experiments.evidence_memory --output-dir runtime/evidence-memory
python -m unittest discover -s tests -p test_evidence_memory_experiment.py -v
```

CLI читает только фиксированный пакет `data/experiments/evidence_memory/`,
проверяет его схемы и SHA256, выполняет 24 случая один раз и пишет:

- `report.json`: hashes входов и реализации, фиксированные параметры, решения
  каждого метода, gold, числители/знаменатели, split-метрики и ресурсная квитанция;
- `report.md`: таблица методов, ошибки и ограничения;
- `evidence-pack/`: точные bytes manifest и трёх JSON-файлов для переносимого повтора.

Stdout содержит компактную JSON-сводку. Код возврата 0 означает прохождение
обозначенной синтетической приёмки, 1 — её нарушение, 2 — ошибку пакета/файлов.
Workflow отдельно фиксирует commit/run; эксперимент не считывает credentials
или переменные GitHub. Wall/CPU seconds измеряются для чтения и оценки до записи
отчёта. Это не замер памяти или полной стоимости хостинга. Model/network calls
равны нулю по конструкции; биллинг облачного runner контролируется отдельно.

## Набор и воспроизводимость

Лицензия данных — [CC0-1.0](../data/experiments/evidence_memory/LICENSE.md).
Два project scope: `alpha`, `beta`; purpose `synthetic-recall`. Фиксированное
время — `2026-09-26T00:00:00Z`, threshold trust=1, payload до 1024 bytes,
не более 8 кандидатов на запрос. 17 вариантов источников и 11 записей реестра;
24 запроса, из них 10 требуют ответа и 14 отказа.

Пакет статический: executor читает закреплённые bytes, ничего не генерирует по
seed. Seed `20260926` и правило `first12hex(SHA256(UTF8(seed + ":" + label_key)))`
документируют создание непрозрачных маркеров; список ключей находится в LICENSE.
Вопросы, порядок кандидатов и изменения полей перечислены явно в JSON.
Повтор одинакового принятого checkout должен воспроизводить `results`, input и
implementation hashes; wall/CPU timing и сведения о платформе могут различаться.

`development` содержит 10 случаев, `synthetic_holdout` — 14. Второй является
**отдельным synthetic regression split**, видимым разработчику. Он не independent,
не blinded и не source-family-disjoint: часть исходных записей повторяется.
В нём есть положительные вопросы новых семейств (tessellation/routing) и
негативные случаи. Gold записан авторами в `cases.json`; это не независимо
проверенная разметка. Метод не получает gold, category или split: evaluator
передаёт только project_id, question и candidate_ids.

Полный UTF8 blob связывает `source_id`, `question` и `answer`; SHA256 относится
ко всем этим bytes. Подмена вопроса или повторное вычисление digest только в
недоверенной записи не изменяют закреплённый trusted digest. `source_id` внутри
payload должен совпасть с record_id; ID варианта кандидата отдельно позволяет
сравнить оригинал и повреждённый вариант одной записи.

## Что сравнивается

| Метод | Правило |
|---|---|
| membership | Первый кандидат с точным question и корректной связкой payload source_id/record_id; membership означает наличие вопроса в предоставленной памяти, а не trusted registry. |
| scope_only | То же плюс наличие ID в trusted registry и точное совпадение project/purpose у record, registry и policy; без проверки digest, trust, времени или отзыва. |
| provenance | Тот же порядок, exact-question и payload binding, затем существующий verifier: scope, trusted threshold, полный digest, связанное время, актуальность и revoked. |

Неподходящий первый кандидат пропускается; поиск продолжается до первого
допустимого или отказа. Это абляция механизмов допуска для exact lookup, не
семантический retrieval, embeddings, обучение или модель человеческой памяти.

Контрпримеры включают чужой scope с тем же ответом, чужой первым и свой вторым,
истечение ровно в valid_until, revoked, низкий trust с required_trust=-1,
удалённую запись, self-rehash подменённого blob, timestamp rebinding, неверный
purpose/source binding и валидные, но нерелевантные in-scope bytes.
`registered_false_claim` намеренно содержит допустимые bytes с неверным маркером:
verifier должен принять целостность, evaluator — отметить wrong_answer.

## Метрики и приёмка

Правильный ответ требует одновременно правильного текста **и** candidate ID из
разрешённых gold source_ids. Совпадение текста чужой записи недостаточно.
Чужая область определяется по выбранной trusted registry entry, а не по ответу
или заявлению недоверенной записи.

| Метрика | Числитель / знаменатель |
|---|---|
| correct_answer_rate | Правильные текст и источник / gold-answer cases |
| correct_refusal_rate | Отказы / gold-refusal cases |
| false_accept_rate (FAR) | Ответы на gold-refusal / gold-refusal cases |
| invalid_accept_share | Все ответы, не являющиеся correct_answer / все выданные ответы |
| foreign_accept_rate | Выбранные чужие источники / cases с хотя бы одним чужим кандидатом |
| expired_accept_rate | Выбранные истёкшие источники / cases с истёкшим кандидатом |
| revoked_accept_rate | Выбранные отозванные источники / cases с отозванным кандидатом |

При нулевом знаменателе rate=`null`, не ноль. Знаменатель invalid_accept_share
зависит от поведения метода. Probe-знаменатели считаются по наличию кандидата,
в том числе нерелевантного/не рассмотренного до раннего ответа; это не доля
среди релевантных или фактически просмотренных записей. Отдельно считаются
wrong_answers, wrong_sources, false_refusals и unknown_source_accepts; эти
ошибки могут пересекаться, их нельзя складывать как непересекающиеся категории.
Все синтетические bytes загружаются в память. Измеряется утечка **выбранного
выходного evidence**, а не запрет чтения чужих bytes.

Минимальная приёмка для provenance: ноль foreign/expired/revoked accepts,
ноль ответов на gold-refusal и хотя бы один правильный ответ в каждом split.
Поэтому отказ всем не проходит. Порог не является утверждением о perfect
accuracy: ожидаемый контрпример registered_false_claim остаётся неправильным
ответом. Статически ожидаются 9/10 правильных ответов и 14/14 правильных отказов;
это проверяемые ожидания, а не сообщение о состоявшемся запуске.

Реестр, policy, clock и manifest доверены как часть принятого checkout. Хеши
обнаруживают расхождение с ним, но не удостоверяют авторство, правдивость или
независимую защиту реестра. Изменивший и dataset, и trusted manifest оператор
может изменить эксперимент. Нет подписи, защищённого main, удалённого trust
anchor, внешней репликации или клинической/научной валидации.

## Методическая основа и рецензии

[Документация Python hashlib](https://docs.python.org/3/library/hashlib.html)
описывает digest для последовательности bytes; поэтому хешируется весь blob,
а проверка целостности не подменяет gold оценки смысла.
[Раздел scikit-learn о data leakage](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)
обосновывает разделение разработки и оценки; здесь явно раскрыта ограниченность
developer-visible regression split. Scikit-learn не является зависимостью.

DeepSeek-011 проверил описание задачи через native чат, без скачивания/запуска
этого пакета; его предложения о разных знаменателях и same-text foreign case
учтены. Независимая статическая рецензия другого агента проверяет реализацию,
но обе рецензии не заменяют cloud tests или независимую научную репликацию.
