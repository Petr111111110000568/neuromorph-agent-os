# Внешние агентные harness: Unreal Agent, Pi и OpenHands

Версия 0.10 добавляет адаптеры к настоящим внешним агентным раннерам. Их код не подменяется собственными правилами Meta-Harness: после проверки локальной установки вызывается закреплённый executable, передаётся публичный запрос и разбирается реальный поток событий. Модельные вызовы по умолчанию отключены. Результат остаётся текстом для проверки; инструменты, изменение проекта и исполнение кода, предложенного моделью, отключены.

Текущие локальные состояния видны командой:

```sh
python -m workbench.harnesses status
```

Отсутствующий бинарник, незакреплённый хеш, установленный SDK и успешный модельный ответ — разные состояния. Реестр не подменяет одно другим. Исторический отчёт о сборке сам по себе не делает новую установку проверенной.

## Установка после клонирования

Ядро работает на Python 3.11+. Внешние адаптеры этой версии запускаются в Linux/WSL. Runtime-файлы не входят в git; на новой машине их нужно создать. Команды выполняются из корня репозитория:

```sh
python scripts/bootstrap_unreal.py --install --pin-registry
python scripts/smoke_unreal.py --output runtime/harnesses/unreal-protocol.json
```

Первая команда получает закреплённые публичные исходники и Go toolchain, проверяет их, собирает runner и записывает локальный pin. Вторая использует локальный тестовый ответ; API-ключ и оплата модели не требуются. Go не нужно заранее устанавливать глобально.

Для Pi нужен Node **22.19+** и npm в PATH:

```sh
python scripts/bootstrap_pi.py --install --pin-registry
python -m workbench.harnesses status
```

Pi устанавливается с закреплённым npm lock и отключёнными lifecycle-скриптами. Флаг `--pin-registry` записывает проверенные хеши локального Node, entrypoint и зависимостей. Для проверки уже установленного Pi используется `python scripts/bootstrap_pi.py --verify --pin-registry`.

После настройки API-ключа через серверный менеджер секретов или окружение включите `AUTONOMY_ALLOW_MODEL_CALLS=true` и перезапустите `python -m workbench local-network`. Веб-панель: **http://127.0.0.1:8765/harnesses.html**. Ключ не следует вводить в поле задачи. Через CLI разрешение задаётся отдельным флагом примера ниже.

## Реализованные интерфейсы

| Harness | Интеграция | Контроль инструментов |
|---|---|---|
| Unreal Agent | Нативный Go `unreal-agent-runner`, stdin JSON → stdout JSONL | `disallowed_tools: ["Bash", "ViewImage", "SkillUse"]` |
| Pi Coding Agent | Закреплённый Node + реальный CLI entrypoint, stdin → JSONL | `--no-tools`, отключение extensions, skills, templates, themes и context files |
| OpenHands | Явная запись возможностей; требуется отдельный внешний worker и установка SDK | Локального запуска SDK этим адаптером нет |

OpenHands возвращает `external_worker_required`. Это не заглушка, выдающая вымышленный ответ, и не заявление, что SDK уже установлен. Наличие адаптера Pi также не доказывает наличие его пакетов: фактическая установка и pin проверяются при каждом запросе статуса/запуска.

## Unreal Agent: проверенный исходный контракт

Исходный репозиторий: [unreallabsai/unreal-agent](https://github.com/unreallabsai/unreal-agent), закреплённый commit `1b9f778453f411c029b39b85102aaefb95e7e48d`.

Изучены `cmd/internal/agentrunner/run.go`, `usage.go`, `providers.go`, `cmd/unreal-agent-runner/tools.go`, `harness/tool/registry.go`, `harness/sessionstore/itemjson.go` и `harness/llm/model.go`. Интеграция использует фактические поля этого commit, а не предполагаемый общий агентный API.

Runner получает JSON с `prompt`, `model`, собственным `system_prompt`, `max_attempts: 1`, `thinking_level: low` и запретом всех трёх известных статических инструментов. `extra_allowed_tools` не используется: upstream принимает, но игнорирует это поле. Пустой список запретов инструменты не отключает.

Upstream всегда пытается читать `.env` и `.harness/skills` в workspace. Поэтому ему выдаётся новый пустой временный каталог; исходники, пользовательская рабочая директория и домашний каталог туда не монтируются и не копируются. Сессии направляются явным `-session-directory` в другой временный каталог того же вызова. После завершения временные файлы удаляются.

Стандартный upstream system prompt утверждает, что агент находится в isolated sandbox container. Адаптер заменяет его: здесь есть ограничения процесса, но нет контейнерной или иной полноценной изоляции безопасности.

Unreal передаёт reasoning effort в Responses API. Поэтому его модель по умолчанию — `gpt-5-mini`; доступность конкретной модели и право API на аккаунте проверяются только реальным ответом. Это не обязательство поставщика сохранить имя модели. Ключ передаётся через `OPENAI_API_KEY`, provider фиксируется `openai`, произвольный base URL из окружения не наследуется.

JSONL Unreal использует поля с заглавных букв: `Kind`, `Data`, `Response`, `Output`. Успех требует кода выхода 0, хотя бы одного `model_response`, `Stop: complete`, отсутствия `Failure` и непустого assistant-текста. Один `rc=0` не считается достаточным: отказ, ограничение выхода и commentary без финального текста получают отдельный статус. Размышления, пользовательские сообщения и произвольные поля событий не отдаются как окончательный ответ.

## Pi: настоящий CLI, отключённые ресурсы

Актуальный изученный upstream — [earendil-works/pi](https://github.com/earendil-works/pi), пакет `@earendil-works/pi-coding-agent`. Точная установленная версия, исходный commit и пути закрепляются в `config/harnesses.json` после сборки. Используются официальные [CLI docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/cli.md) и [JSON docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/json.md).

Реальный entrypoint запускается закреплённым Node, без перехода через `.bin/pi` symlink. Проверяются хеши Node, entrypoint и всего дерева установленных пакетов. Изменение зависимого JS-файла также делает pin недействительным. Выходящие за дерево symlink отклоняются. Это контроль целостности доверенной установки; он не превращает сторонний код в недоверенную программу, которую можно безопасно исполнять на произвольном хосте.

Флаги запуска:

```text
--mode json --no-session --no-tools --no-extensions --no-skills
--no-prompt-templates --no-themes --no-context-files --no-approve --offline
--provider PROVIDER --model MODEL --system-prompt FIXED_SYSTEM_PROMPT
```

Запрос передаётся **через stdin**. Он не становится позиционным аргументом: в Pi синтаксис `@path` мог бы означать чтение вложения даже после `--`. В stdin эти символы остаются обычным текстом. Это отдельно проверено регрессионным тестом.

Pi получает свежий `PI_CODING_AGENT_DIR`; старые OAuth-файлы и настройки аккаунта не импортируются. `PI_OFFLINE=1`, `PI_SKIP_VERSION_CHECK=1` и `PI_TELEMETRY=0` подавляют фоновые обновления каталога, проверку версии и телеметрию в пределах документированного поведения upstream. Явный модельный вызов с API-ключом разрешается отдельно. Эти флаги не являются сетевым firewall для произвольного изменённого стороннего кода.

Парсер ждёт завершения процесса, успешный assistant `message_end` с `stopReason: stop` и `agent_settled`. Событие `agent_end` само по себе не финальное: после него upstream может продолжить повтор или обработку очереди. JSONL разделяется байтом LF, а не любыми Unicode-разделителями строк; символ U+2028 внутри текста допустим.

## Запуск с моделью

После проверенной установки и настройки соответствующего API-ключа на стороне сервера:

```sh
python -m workbench.harnesses run unreal --prompt "Предложи критерии воспроизводимости вычислительного эксперимента" --allow-model-calls --model gpt-5-mini
```

Для Pi доступны явные providers `openai` и `anthropic`, если установленный пакет поддерживает выбранную модель. Флаг `--allow-model-calls` разрешает платный вызов этого локального запуска. Он не создаёт ключ, аккаунт или подписку. По умолчанию возвращается `blocked_model_calls_not_allowed`; без соответствующего ключа — `blocked_provider_missing`.

Веб-интерфейс и MCP используют те же адаптеры, но серверный контроль разрешений на модель задаётся отдельно. Сам внешний runner не получает полномочия изменять проект или доступ к журналу остальных сессий. Входной prompt должен содержать только информацию, которую разрешено отправлять выбранному API-поставщику.

Собственная реализация `workbench.autonomy` версии 0.9 сохраняет отдельный контракт одного ограниченного HTTP-запроса. Свободный агентный harness не подменяет этот цикл и не наследует его бюджетные гарантии.

## Ограничения процесса и бюджета

Используются `subprocess` без shell, отдельная POSIX process group и фиксированный доверенный Python launcher для `resource.setrlimit` перед `execve`. Это позволяет запускать адаптер из многопоточного веб-сервера без пользовательского Python `preexec_fn`.

- Prompt: до 32 000 байт UTF-8.
- Совокупный stdout + stderr: до 256 KiB.
- Wall time: от 1 до 60 секунд по запросу; по умолчанию 30.
- CPU: мягкий предел 30 секунд, жёсткий 31.
- Размер каждого создаваемого файла процесса: до 8 MiB; открытых файлов — до 128; core dump отключён.
- Виртуальное адресное пространство Unreal: 2 GiB; Pi: 16 GiB для резервирования V8, с `--max-old-space-size=256` для JS heap. Виртуальный лимит не равен физически занятой памяти или совокупному лимиту всех потомков.

Чтение stdin/stdout/stderr неблокирующее. При превышении времени, объёма вывода или появлении инструментального события процессная группа прекращается. После обычного выхода родителя оставшиеся потомки также завершаются. Эти меры рассчитаны на доверенные закреплённые раннеры: намеренный выход произвольного вредоносного процесса из process group не заменяет защиту ядром или контейнером.

В дочернем окружении нет унаследованных proxy, `HOME`, auth/base-URL overrides, посторонних секретов и настройки shell. Передаются только фиксированные служебные переменные, временные пути и один явно выбранный API-ключ. Upstream HTTP redirect policy отдельно не переписана; отсутствие унаследованного proxy не означает запрета перенаправлений на уровне HTTP-клиента upstream.

**Wall time и объём stdout не являются лимитом API-токенов, запросов или расходов.** `max_attempts: 1` отключает повтор отдельного Unreal-запроса, но не гарантирует один модельный turn за сессию. Нативный runner этого commit не выставляет общий token/cost budget. Неожиданные tool calls немедленно обрываются при чтении событий, однако их отсутствие не доказывает ровно один HTTP-запрос. Расходы контролируются ограничениями аккаунта API-поставщика; автоматический фоновый запуск этих harness по расписанию не включён.

В текущей реализации запуск ограничен POSIX/Linux; для Windows нужен Linux/WSL. Это ограничение относится к внешним harness-адаптерам, а не ко всему ядру Meta-Harness. Отдельный cwd и процессные лимиты не являются безопасной песочницей для недоверенного кода.

## Результаты и достоверность статусов

Публичный API модуля:

```python
from workbench.harnesses import HarnessRegistry

registry = HarnessRegistry(project_root)
status = registry.status()
result = registry.run("unreal", public_prompt, allow_model_calls=False)
```

У результата есть `status`, `output_text`, `counts`, `execution` и `evidence` с revision/хешем executable. Сырые stderr и полные JSONL-сессии в результат не включаются. Известный переданный ключ проверяется как в сырых байтах вывода, так и после декодирования JSON, включая `\u`-экранирование. Сообщения ошибок API не отражаются пользователю произвольно; это точная защита известного credential, а не универсальная проверка конфиденциальности любого текста.

Статусы различают отсутствие установки, неверный pin, запрет вызова, нехватку ключа, ошибку runner, timeout, ограничение вывода, незавершённый ответ, инструментальное нарушение и успешный текстовый ответ. Для OpenHands всегда явно указана необходимость внешнего worker.

При успешном запуске создаётся небольшой локальный receipt в `runtime/harnesses/<id>.last-run.json`. В нём нет prompt, ключа или ответа модели. Поля `protocol_tested` и `live_authenticated` привязаны к текущему revision и хешу установленного executable; для Pi дополнительно проверяются хеши Node и дерева пакетов. Без совпадения всех проверенных pins они не показываются как подтверждённые. Эти флаги фиксируют прошлый успешный запуск данной установки, а не непрерывную доступность API.

`protocol_tested` означает проверку протокола с локальным тестовым endpoint и искусственным ключом. `live_authenticated` означает успешный запуск через обычный provider path; после теста локального endpoint этот флаг остаётся false. В публичном веб/API путь к mock endpoint не принимается. Протокольный тест не доказывает оплату API, подключение пользовательской подписки или научную полезность ответа.

## Проверки

`tests/test_harnesses.py` проверяет реальные доверенные fixture-процессы: запрет вызова по умолчанию, пустой workspace, отсутствие ambient secrets и proxy, отключение всех Unreal tools, pin/receipt, symlink, timeout, ограничения вывода, завершение дочернего процесса, корректное ожидание после EOF, немедленный обрыв tool-события и JSON-экранированный credential echo. Дополнительно проверены форматы Unreal/Pi, `agent_settled`, безопасная передача Pi `@path` через stdin и целостность дерева зависимостей.

Fixture-процессы созданы разработчиком как тестовый код; это не запуск кода, сгенерированного моделью. Реальная сборка Unreal и его полный локальный HTTP-протокольный тест выполняются отдельными скриптами `bootstrap_unreal.py` и `smoke_unreal.py`. Фактические текущие результаты установки Pi и живых модельных вызовов следует читать в отчёте версии и текущем `harnesses status`, не выводить их из существования адаптера.
