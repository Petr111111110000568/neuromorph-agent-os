# M02: минимальный диспетчер проектов поверх существующей Queue

Статический проект спецификации, 26.09.2026. Это требования и план проверки, не реализованная функция. Код и тесты локально не запускались. Основание: `docs/PROJECT_MISSION_AND_ACCEPTANCE_RU.md`, фактические `workbench/network/queue.py`, `network/control.py`, `brain.py`, `society/control.py`, `network/worker.py` и `tests/test_network_queue.py`.

## Что уже реализовано и повторять не нужно

| Механизм | Существующая реализация | Граница |
|---|---|---|
| Атомарная аренда, срок, смена владельца | `Queue.claim/heartbeat/finish`, SQLite `BEGIN IMMEDIATE`, случайный токен и сохранённый digest | Один локальный координатор; SQLite не является общей сетевой БД |
| Повторная доставка и несовместимый вход | `Queue.submit` с idempotency key + submission fingerprint; `finish` с completion fingerprint | At-least-once исполнение, а не exactly-once внешний эффект |
| Восстановление после частичного enqueue | `Queue.by_idempotency_key`; Brain/Society/Network control используют устойчивые ключи между раздельными транзакциями | Нужен тот же ключ и тот же контракт, не новая случайная задача |
| Отмена и поздний ответ | `Queue.cancel`; Brain сначала сохраняет cancellation intent | Начатое вычисление может закончиться, но результат лишён права записи |
| Ограничение попыток и доступный worker | `max_attempts`, capability routing, одна live lease на worker | Нет общего project backlog, межпроектного бюджета и review task result |

Не добавлять вторую таблицу lease, собственную генерацию токенов или новый claim/finish протокол. M02 использует существующий класс Queue и его regression tests. Для конечной демонстрации допустим отдельный экземпляр этой Queue в одном cloud runner, чтобы synthetic jobs не конкурировали с настоящим backlog.

## Минимальный новый слой

Один `ProjectDispatcher` со stdlib/SQLite: карточки двух проектов, карточки задач, текущий handoff, reviewer decision, durable intent/event log. Хранение control-метаданных отдельно от Queue допустимо по уже применяемому паттерну Brain. Реализация должна документировать границу двух commit и её recovery, не обещать общую транзакцию двух БД.

Карточка проекта: фиксированные `project_id`, миссия, разрешённые публичные артефакты, критерии закрытия и операторская resource policy. Карточка задачи: `task_id`, `project_id`, конечная цель, зависимости, `revision`, `handoff_id`, `base_commit`, canonical input SHA256, allowlisted handler, queue job ID, review/result/checkpoint, ограничения. Входные dict имеют закрытую схему и конечные ограничения размеров/числа задач. Не принимать URL/команду/плагин из результата как исполняемый handler.

Для первой версии: максимум 2 активных проекта, 1 незавершённое исполнительское задание на проект, 8 задач суммарно, 2 queue attempts на handoff, общий заранее заданный предел 8 резервируемых попыток и 0 платных/модельных вызовов. Это политика демонстрации; цифры не повышают и не заменяют квоты действующего continuous. M02 не читает и не сбрасывает ledger Qwen.

Ключ Queue: `m02:` + SHA256 канонического `[project_id, task_id, handoff_id, input_sha256]`. Он укладывается в текущие 128 символов и связывает одинаковый текст разных проектов с разными заданиями. `input_sha256` покрывает весь принятый контракт задачи, а не только вопрос. Существующий fingerprint Queue дополнительно проверяет собственный payload/capabilities/max_attempts.

Не добавлять project metadata в текущий payload worker наугад: `network.worker._execute` имеет строгий allowlist полей. Synthetic demonstration использует отдельный фиксированный fake executor, который вызывает реальную Queue, принимает только заранее заданные fixture IDs и возвращает фиксированные JSON-артефакты без исполнения команд. Это проверка диспетчера, не новый удалённый агент. Подключение реальных handlers — отдельный последующий контракт.

## Один конечный tick

1. Сначала сверить уже завершённые queue jobs и незавершённые intents, затем выполнить ожидающее review/восстановление. Лишь после этого выбирать новую готовую задачу. Причина выбора записывается: зависимости закрыты, канал доступен, есть ресурс; среди равных — стабильный порядок с чередованием проектов.
2. Под SQLite transaction проверить expected task revision, отсутствие конфликтующей активной задачи, доступный общий ресурс. Сохранить неизменяемый dispatch intent и **зарезервировать сразу max_attempts** до Queue.submit. Это позволяет текущей Queue повторить потерянную аренду, не превысив общий лимит. Результат исполнителя никогда не меняет resource policy или счётчики. В первой версии резерв монотонен: устаревший результат, отказ публикации и crash не возвращают потраченные попытки или зарезервированный лимит.
3. Отправить тот же контракт с тем же idempotency key; сохранить job ID. Сбой после commit Queue до commit control восстанавливается через `by_idempotency_key`, без нового job и повторного списания резерва. Сбой до Queue.submit повторяет тот же intent.
4. Worker может создать только временный/content-addressed результат. Существующая Queue.finish принимает его под актуальной арендой. После этого **одна транзакция control DB** проверяет project/task identity, текущие handoff/input SHA, expected project/task revisions и допустимый статус; в той же транзакции она продвигает указатель на hash результата и сохраняет уникальный publication intent/outbox. Проверка revision отдельным чтением перед последующей безусловной записью запрещена. Нулевой результат CAS означает `stale_for_publication`: сохранённый queue result остаётся историческим результатом прежнего handoff; текущий артефакт не меняется, попытки и резерв не возвращаются.
5. Отдельное review фиксирует hash проверенного результата и `accepted`, `rejected` или `inconclusive`. Принятие закрывает задачу. Замечание создаёт ограниченную новую revision/handoff с родительской ссылкой, сохраняя прошлый результат; exhausted budget оставляет явную паузу. Авторский статус success не заменяет review.
6. При отсутствии допустимого действия tick возвращает `waiting` с причиной и завершается. Один недоступный synthetic channel не блокирует независимый проект. Бесконечного цикла или автоматического paid fallback нет.

Checkpoint M02 первой версии — последний подтверждённый этап/результат, текущий intent и очередь. Не заявлять возобновление произвольного процесса с середины инструкции. Живую промежуточную запись под lease не добавлять, пока для неё не задан и не проверен отдельный fenced API.

## Уточнение после DEEPSEEK-012: очередь и публикация — разные границы

Источник замечания — финальный тезис нативного DEEPSEEK-012, переданный координатором для проверки; весь диалог в этой проверке не перечитывался. Предложение модели не считается подтверждённым дефектом. Проверка фактического `workbench/network/queue.py` установила:

- `claim`, строки 262–289, увеличивает attempts при выдаче аренды. `finish`, строки 314–345, **не** увеличивает attempts; он сохраняет result и completion fingerprint. Перенос учёта попыток в finish не нужен и может перестать учитывать уже выполненное, но потерянное вычисление.
- Успешный finish сохраняет результат. После crash `get` или `by_idempotency_key` (строки 359–375) находит completed job вместе с результатом; повтор идентичного finish также предусмотрен при сохранённом токене. Commit не делает результат невосстановимым. Токен не нужен координатору для чтения уже завершённого job.
- Сценарий «finish для R1 → проект перешёл в R2 → координатор обнаружил несовпадение и отказал в публикации» — правильное отклонение устаревшей работы. Оно не доказывает потери результата. Исторический результат R1 сохраняется, но не становится текущим результатом R2.
- Реальная опасность: «координатор отдельно прочитал/проверил R1 → другой координатор записал R2 → первый безусловно продвинул указатель старого артефакта». Приёмка должна воспроизвести именно это чередование. Защита находится в атомарном CAS **control state + artifact pointer/outbox**, а не в добавлении project revision только в Queue.finish.

Если внешний Git/артефактный сервис участвует в публикации, локальная транзакция и его запись не становятся атомарными от самого наличия outbox. Первая версия публикует неизменяемые versioned artifacts/receipts, а актуальность определяется авторитетным control pointer. Доставка outbox повторяется с устойчивым event ID и expected target revision/hash; конфликт или superseded intent не перезаписывает новую версию. Отдельный mutable указатель внешнего сервиса требует собственного CAS-протокола и явного правила синхронизации; нельзя обещать атомарное переключение двух независимых хранилищ. Outbox здесь обеспечивает восстановление доставки, не возврат ресурсов и не распределённый commit.

## Облачная демонстрация и сохранение

Два **отдельных** конечных GitHub Actions run на точном проверенном commit. Run A формирует два synthetic проекта, выполняет ограниченные jobs, сохраняет подтверждённый этап и завершает процесс. Run B получает конкретный `previous_run_id`, сверяет repo/workflow/branch/commit и manifest SHA, восстанавливает сохранённые control/Queue DB и продолжает без сброса attempts/revision/бюджета. Не выбирать непроверенный «latest artifact»; пропавший/просроченный artifact означает `resume_unavailable`, а не новую инициализацию с полным бюджетом.

БД сохранять согласованным SQLite backup либо после закрытия всех соединений; не копировать один основной SQLite файл при живом WAL. Входящие модельные артефакты не могут задавать snapshot DB. Для демонстрации snapshot содержит только собственные synthetic данные и служебные lease digests; raw lease tokens/API secrets не сохраняются. В публичную краткую квитанцию и журнал не экспортировать внутренние digests или токены. Persistent artifact с конечным retention — доказательство двух запусков, не обещание бессрочного hosting.

Public receipt: schema/source commit/run ID/previous run ID/input and state hashes, выбранные task IDs и причины, переходы, фактические attempts/reservations, duplicate suppression count, stale rejection count, result hashes/review outcomes, ограничения. Queue.completed означает окончание вычисления, не принятие научного вывода.

## Приёмка: реальные контрпримеры

| Проверка | Наблюдаемое условие успеха |
|---|---|
| Два проекта с одинаковым вопросом | Разные task/handoff/job IDs и scope; результат одного не закрывает другой |
| Два конкурентных tick/claim | Один intent/резерв/job на handoff; одна действующая аренда, общий лимит не превышен |
| Crash сразу после Queue.submit | Recovery на той же БД находит тот же job; число задач и резерв не увеличиваются |
| Crash сразу после успешного finish, до control promotion | Recovery читает тот же completed job/result через get/idempotency lookup; повторного claim/вычисления/резерва нет |
| Повтор finish | Те же bytes возвращают тот же результат; другие bytes отклоняются |
| Expiry → новый claim → старый finish | Старый ответ не меняет ни Queue result, ни текущий artifact; max_attempts сохраняется |
| Подмена input/revision/handoff | Тот же ключ с иным контрактом отклоняется; новая разрешённая revision не может быть закрыта старым result |
| Проверен R1 → конкурентно записан R2 → promotion R1 | Atomic control CAS отклоняет R1; pointer/revision R2 не меняются, publication intent R1 не становится текущим |
| Устаревший result уже сохранён в Queue | Сохраняется исторический result/hash и расход попытки; отсутствие публикации не возвращает резерв и не открывает обход лимита |
| Crash после control commit до доставки outbox | Возобновляется тот же event ID/артефактный hash, без второго promotion; поздняя доставка не заменяет более новую версию |
| Подмена квоты в result | Поля policy/attempts/max_attempts не принимаются из результата; exhausted budget остаётся exhausted после restart |
| Review двух результатов | Один accepted и закрыт, другой возвращён с конкретным замечанием и сохранённым прежним hash |
| Недоступный канал/зависимость | Другой проект продвигается; выбранная следующая задача и причина ожидания воспроизводимы |
| Два реальных cloud run | Run B ссылается на run A и manifest hash; checkpoint/attempts/revision сохранены, заново ничего не bootstrap-ится |
| Плохой checkpoint | Несовпадающий producer/hash/commit, отсутствие manifest и неподдерживаемая schema дают ограниченный отказ без reset |

Не переписывать уже имеющиеся Queue unit tests под другими именами. Новые тесты должны проверять добавленные стыки project revision → durable intent → Queue → artifact/review и общий бюджет. Существующие concurrency/expiry/redaction tests Queue остаются обязательным regression набором. Все project tests и doctor выполняются только в разрешённом облаке.

Минимальные артефакты реализации: модуль dispatcher, один фиксированный project-template/fixture pack, focused integration tests, конечный scenario CLI, cloud workflow с явным resume input, две фактические cloud receipts. Ни новая регистрация, ни ещё один model API call для закрытия M02 не нужны.
