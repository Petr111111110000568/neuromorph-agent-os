# Закрытый CPU-исполнитель M02

Задание `M02-CPU-IMPL-001`, родитель `qwen-deepseek`, база `898162ee6208be03c5d5cf294c3d264f10f7de1b`; независимый аудит `M02-CPU-AUDIT-001`. Реализуется только [согласованный контракт](M02_CPU_HANDLER_CONTRACT_RU.md) `m02.cpu.coupled.v1`. Результаты проверки конкретного commit следует смотреть в GitHub Actions и квитанции эксперимента; наличие этого документа не означает успешный запуск.

## Приём задания

`ProjectDispatcher(..., cpu_root=trusted_checkout)` принимает CPU-задачу с обычными полями task/project/goal/dependencies/revision/handoff/base_commit/handler/limitations и полным объектом `parameters` вместо `fixture_id`. Требуются все восемь числовых параметров. Имя алгоритма, команда, URL, путь и собственный набор pins во вход не допускаются. Принятый `base_commit` и шесть SHA256 builtin-файлов закреплены в коде адаптера; ответ модели либо содержимое Queue не могут заменить этот реестр.

После сверки принятого control-контракта создаётся закрытый вход с `schema_version`, project/task/revision/handoff/parent/base, handler, parameters и `input_sha256`. Резерв и фактические попытки учитываются прежним общим M02 бюджетом: две попытки на handoff, максимум восемь резервов, без сброса при рестарте или R2.

## Отдельный маршрут

Queue kind/capability `m02_cpu` отделён от `simulation` и `evidence`. Обычный network worker не объявляет эту возможность и не забирает такие задания. Доверенный конечный вход — `workbench.m02_cpu.run_cpu_once(dispatcher, root=trusted_checkout)`; он обращается только к существующему `Service.run` с постоянным `plugin_id='coupled_dynamics'`. Это локальный доверенный адаптер к control DB, а не новый публичный endpoint или произвольный удалённый исполнитель.

Перед исполнением сверяются вход, принятый handoff, сохранённый резерв и Queue identity. Результат получает отдельный детерминированный `scientific_sha256`; UUID, Python/OS, время и ограничения процесса сохраняются отдельно в provenance. Принимается закрытая схема шести рядов, трёх метрик, двух строк таблицы и фиксированного описания модели.

## Восстановление и проверка

В control DB сохраняется результат до `Queue.finish`. После потери подтверждения завершённая очередь читается повторно; новый handoff не создаётся. Сохранённый результат можно использовать после восстановления аренды, сохраняя счётчик попыток. При прерывании до любой durable-записи результата допустим повтор чистого расчёта только в оставшейся попытке уже зарезервированного задания. Это не exactly-once вычисление.

Workflow `M02 bounded CPU experiment` запускает конечный опыт в двух jobs одного проверяемого run. Seed считает отрицательный контроль `perturbation=0` и пару `coupling=0/1`; на третьем результате дочерний процесс завершает работу кодом 71 после durable `Queue.finish`. Checkpoint загружается другим job строго из того же run; SHA manifest передаётся через зависимость jobs. Resume сверяет файлы/identity и заранее заданную проекцию B, публикует сохранённый результат без вызова CPU-worker и проверяет повтор B.

Отдельно проверяются нулевая разность при нулевом воздействии, сохранение среднего до `1e-12` при смене coupling и ненулевое изменение локальной компоненты. Квитанция содержит реальные ряды и хеши, численные невязки, попытки и резерв. Focused тесты покрывают неправильные входы, pins, routing, конкурентность, устаревший R1 и границы восстановления; их запускает CI, включая Windows/macOS/Linux portability.

Модель безразмерная, `calibrated=false`, клиническая или биологическая валидация не заявляется. Вызовов модели/сети и дополнительных расходов у адаптера нет. Отдельный Python-процесс не является ОС-песочницей; Windows не получает POSIX CPU/RAM limits. Просмотр и импорт исторических квитанций Studio остаются отдельной операцией и не запускают этот handler.
