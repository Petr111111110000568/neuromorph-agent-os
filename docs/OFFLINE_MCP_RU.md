# Локальный совет через MCP

Реализован серверный интерфейс трёх действий для установленной локальной модели: просмотр, один конечный запуск и остановка. Он использует тот же `service.offline`, журнал запросов и ограничения, что `/offline.html`. Это локальный stdio-процесс, без облачного MCP endpoint, сетевого listener, OAuth или доступа к чужим аккаунтам. Добавление конфигурации клиента и успешный модельный ответ — отдельные этапы проверки.

| Инструмент | Аргументы | Результат |
| --- | --- | --- |
| `offline_council_status` | `{}` | Сохранённые квитанции и состояние потока текущего контроллера. Наличие manifest не доказывает целостность весов или завершение модели. |
| `offline_council_start` | Ровно `question`, `request_id`, `public_data_confirmed` | Сначала сохраняет резерв, затем запускает существующий конечный движок. Возвращает `id` и признак подавления повтора. |
| `offline_council_stop` | `{}` | Создаёт STOP для незавершённых запросов в общей директории состояния. Это запрос остановки; завершение проверяется через status. |

`question` — непустая строка до 2000 символов; `request_id` — до 80 букв, цифр или дефисов; `public_data_confirmed` — именно JSON `true`, после проверки оператором, что текст публичный. Пробельные строки и NUL отвергаются контроллером. Дополнительные поля, включая путь исполняемого файла, другую модель, shell-команду, источник credentials или права, не допускаются. Один и тот же ID с тем же текстом возвращает существующую запись; с другим текстом — конфликт. Повтор не означает повторную генерацию. При busy или ненастроенной модели нет скрытого retry/fallback.

Пример аргументов запуска:

```json
{
  "question": "Предложи конечную проверку дедупликации задач и конкретный контрпример к ошибочному решению.",
  "request_id": "public-research-001",
  "public_data_confirmed": true
}
```

## Команда и ограничение возможностей

Из корня проверенного checkout:

```sh
python -m workbench --data-dir ./state mcp --offline-only
```

`--offline-only` ограничивает серверную выдачу **и исполнение** ровно тремя перечисленными инструментами. Скрытый вызов другого имени отклоняется. Старый `mcp` без флага сохраняет полный существующий интерфейс; для этого подключения его использовать не следует. Клиент выполняет `initialize`, `notifications/initialized`, затем `tools/list` / `tools/call`. Это документированный stdio subset MCP 2025-11-25, а не полная реализация протокола.

Чтобы IDE с другим рабочим каталогом не загрузила непроверенную копию проекта, используйте `scripts/run_offline_mcp.py` именно из проверенного runtime. Он определяет корень по собственному файлу, добавляет его в import path и всегда вызывает `mcp --offline-only`. Принимается только `--data-dir`; выбор модели, shell и сетевой адрес не настраиваются через launcher.

```sh
python -I /path/to/verified/repo/scripts/run_offline_mcp.py --data-dir /path/to/shared/state
```

Это шаблон пути. В Windows укажите локальный `python.exe` из отдельного venv и реальные пути к проверенному runtime. `-I` исключает пользовательский Python site и переменные окружения Python из поиска модулей; это не файловая или сетевая ОС-песочница.

## Visual Studio: подготовленный, не активированный пример

Пример находится в `examples/mcp/visual-studio-offline.json`. Файл с placeholders в `examples/` не является установленным MCP-сервером и не запускается автоматически. Оператор сначала выбирает проверенный runtime и общую директорию состояния, заменяет три `<PATH_...>` и только затем переносит запись в конфигурацию решения. Личных путей, ключей и auto-confirm в шаблоне нет.

Официальная документация Visual Studio указывает `.mcp.json` в каталоге решения и выбор инструментов через Agent → Tools. При обнаружении конфигурации IDE может начать handshake; поэтому шаблон намеренно хранится вне автоматически обнаруживаемых мест. Инструменты включаются оператором. Источник: [Microsoft Learn: MCP в Visual Studio](https://learn.microsoft.com/en-us/visualstudio/ide/mcp-servers?view=visualstudio).

Схема примера использует `servers`, `type: stdio`, `command`, `args`, `env`. VS Code имеет собственную `.vscode/mcp.json` с этими полями; его настройки sandbox на Windows не действуют. Не путать клиенты и не считать выбранную оболочку подтверждением живого подключения: [справочник VS Code](https://code.visualstudio.com/docs/agents/reference/mcp-configuration).

После ручного подключения сначала проверьте, что `tools/list` содержит ровно три имени. Затем проверьте status и один согласованный несекретный запрос. Модельные ответы, полученные клиентом IDE, могут включаться в контекст внешнего Copilot: локальное исполнение модели не делает облачного клиента офлайн. Для полностью автономной от сети работы используйте локальную веб-панель или локального MCP-клиента.

## Жизненный цикл, ресурсы и достоверность

- Веб-панель и MCP должны использовать **одну** директорию состояния: OS-lock и дедупликация привязаны к ней. Разные state-каталоги не образуют общей блокировки GPU. Отдельный CLI движка также не входит в эту блокировку контроллеров.
- Доступен один активный совет в этой директории, до 24 записей истории. Профиль закреплён в существующем движке: Qwen3-14B Q4_K_M / llama.cpp b11146 / Windows Vulkan0. Это не локальные веса Kimi K3 и не три независимые модели.
- Текст ответа остаётся предложением. MCP не исполняет его как код, не выдаёт новые права и не запускает внешние инструменты. Локальные выводы не доказывают научную валидацию.
- Обычный EOF/выход CLI вызывает `Service.close()`: контроллер пишет STOP только для собственного активного запуска и ждёт его до 6 секунд. Просмотр статуса в другом клиенте не останавливает работу веб-панели. Явный `offline_council_stop` имеет более широкий scope — все pending записи этой state-директории.
- Принудительное убийство процесса IDE, выключение питания или некооперативный native-процесс не дают гарантии graceful shutdown. Сохранённый резерв не переотправляется автоматически; после сбоя нужен осмотр квитанции и процессов. Сервер не является постоянным облачным worker.
- Unit-проверки используют fake runner без модели и сети. Они проверяют точность схем, capability allowlist, dispatch, CLI EOF и владение остановкой. Факт проверки на конкретном commit берётся из cloud CI, а не из наличия тестовых файлов.

Удалённый HTTP/cloud API для offline council остаётся закрытым существующим сервером. Этот MCP-профиль не расширяет облачные разрешения и не подключает внешние навыки OpenClaw/Hermes.
