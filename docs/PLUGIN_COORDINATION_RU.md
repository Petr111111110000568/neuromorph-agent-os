# Состав плагинов агентов

Механизм управляет профилями `author`, `reviewer`, `reviser` в самом проекте. Он использует семь существующих builtin-плагинов: `structural_plasticity`, `coupled_dynamics`, `regression_benchmark`, `quantum_circuit`, `legacy_topology`, `kan_benchmark`, `cortical_sequence`. Перед каждой операцией проверяются все шесть файлов из `data/builtin_pins.json`; ID и версии извлекаются из AST реестра без импорта или исполнения кода.

Плагины приложения Codex — отдельные установленные расширения. Этот модуль не устанавливает их, не получает доступ к их аккаунтам и не выдаёт согласия от имени пользователя. Установка произвольного кода из URL, изменение credentials, сетевых разрешений и платные вызовы не поддерживаются.

## Облачный запуск

Запускать проектный код и тесты только в Colab/GitHub Actions согласно текущему поручению пользователя. Доверенный шаг workflow может выполнить:

```sh
env -i PATH="$PATH" LANG=C.UTF-8 python3 -m workbench.autonomy.plugin_coordination bootstrap > plugin-profile-receipt.json
```

`bootstrap` явно создаёт профильное состояние, если его ещё нет, и проводит три детерминированных изменения: author → reviewer, reviewer → author, author → reviser. Для каждого изменения сначала строится проверяемый план, затем сравниваются SHA256 плана, версия состояния, каталог и закреплённые файлы. Все семь существующих builtin-плагинов включаются в каждом профиле. Модель не вызывается; содержимое модельного ответа не исполняется. Повторный запуск с сохранённым состоянием возвращает `changes: []`.

Receipt содержит `configuration_only: true`, `execution_allowed: false`, `model_calls: 0`, итоговые профили и хеши планов. Это подтверждение конфигурации, а не запуска или научной валидации плагинов.

Состояние и журнал находятся в одном атомарно заменяемом файле `runtime/plugin-coordination/state.json`. Его нужно переносить между эфемерными runner через доверенное хранилище workflow. Сам модуль не загружает состояние в GitHub и не располагает токенами. Без такого переноса каждый bootstrap на новом runner создаёт только конфигурацию этого запуска. Обычные операции `apply`, `status`, admission hook при отсутствующем состоянии прекращаются; неявного сброса нет.

## Предложения между агентами

В `continuous.py` механизм уже встроен в облачный цикл. Модель получает состав трёх профилей и разрешённые ID. Необязательный `plugin_change` содержит `target`, `enable`, `disable`, `reason`; actor, версия и SHA каталога задаются доверенным контроллером. В finalize допустимое предложение применяется автоматически как конфигурация профиля и сохраняется в `plugin_profiles` внутри того же Git-журнала `autonomy/continuous`, вместе с `plugin_receipt`. Здесь остаются последние восемь профильных изменений, полная история — в Git. Старые состояния мигрируют без сброса попыток; отклонение предложения не стирает исследовательский ответ. Это сохранение конфигурации между запусками, не исполнение кода плагинов.

Агент может передать только JSON предложения с полями `schema_version`, `catalogue_sha256`, `expected_revision`, `actor`, `target`, `enable`, `disable`, `reason`. Источник и адресат должны быть разными известными ролями. Дополнительные поля, URL вместо ID, секреты в качестве новых полномочий, самоназначение `approved` и устаревшая revision отклоняются.

В доверенном облачном контроллере доступны команды:

```sh
python3 -m workbench.autonomy.plugin_coordination catalogue
python3 -m workbench.autonomy.plugin_coordination status
python3 -m workbench.autonomy.plugin_coordination propose --actor author --target reviewer --disable quantum_circuit --reason "Сократить профиль текущей задачи" > proposal.json
python3 -m workbench.autonomy.plugin_coordination evaluate --proposal proposal.json
python3 -m workbench.autonomy.plugin_coordination apply --proposal proposal.json --plan-sha256 SHA256_ИЗ_EVALUATE
python3 -m workbench.autonomy.plugin_coordination rollback --expected-revision ТЕКУЩАЯ_REVISION
```

План должен получать и применять доверенный контроллер. Хеш плана защищает от изменения проверенного предложения; сам по себе он не является аутентификацией агента. Полномочия контроллера определяются workflow и правами на файлы. Модель не должна получать файловые права записи на policy, pins, каталог или состояние и не должна сама запускать CLI `apply`.

Проверяются роли, зависимости, конфликты, версии и ресурсные резервы. На один включённый builtin зарезервировано 6 CPU-секунд и 512 MiB — существующие пределы POSIX worker. Общий предел профиля — семь плагинов, 42 CPU-секунды, 3584 MiB. Это консервативная проверка допуска состава; измерение нагрузки и применение лимитов остаются у существующего runner. ОС-процесс не является полной песочницей. Windows не получает новых гарантий POSIX-лимитов от этого модуля.

Журнал ограничен последними 64 изменениями, содержит предыдущий и новый состав целевого профиля, SHA256 предложения и цепочку хешей. Revision растёт и при откате, поэтому старое предложение не становится снова применимым. `rollback` отменяет последнее изменение состава отдельной записью; исходный код, pins, policy и credentials не откатываются. Сбой записи до атомарной замены сохраняет предыдущее состояние. OS-lock не допускает параллельных писателей. Хеш-цепочка выявляет повреждение данных; она не заменяет доверенное хранение и не защищает от владельца, способного переписать весь журнал.

## Подключение к выполнению

Для запуска уже существующего плагина контроллер должен сначала вызвать `require_enabled(agent, plugin_id, root)`, затем отдельно передать разрешённое задание существующему проверенному builtin runner. Admission hook ничего не исполняет. Публичный `service.run` пока не использует этот hook автоматически: подключение делает сопровождающий код отдельной проверяемой правкой. Профиль нельзя считать глобальным запретом обхода старых API до такого подключения.

Добавлен `tests/test_plugin_coordination.py`: проверки закреплённых файлов, статического реестра, предложения/плана, ресурсов и совместимости, CAS, отката, сбоя atomic replace, OS-lock, bounded журнала и идемпотентного bootstrap. При подготовке локальное выполнение не проводилось; результаты облачного CI следует фиксировать отдельно.
